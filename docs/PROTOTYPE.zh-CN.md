# v0.2：怎样运行和理解协议原型

## 这是什么

一版可以运行的单进程 Go 研究模型。它走通签名加密、节点承诺、共同登记、容量队列、服务锁序、条件解密和市场执行，输出事件及可独立核查的签名矛盾。不是生产协议，也不是已经实现的去中心化预测市场。

| 部件 | v0.2 的实际实现 |
|---|---|
| 内层订单授权、外层包签名、节点声明 | Go 标准库 Ed25519 真签名 |
| 订单正文加密 | 每单随机 256 位密钥，AES-GCM，公开头部作为附加认证数据 |
| 门限部分 | **理想密钥保管器**：集中保存完整 AES 密钥，收到足够有效签名批准后才打开；没有门限密文、DKG 或真实解密份额 |
| 共同登记和服务最终确认 | **理想协调器**：验证并合并清单，模拟最终确认；没有实现网络共识 |
| 网络 | 单进程虚拟时间事件队列，各成员维护独立收件状态 |
| 市场 | 一笔固定价格、库存已锁定的 YES 卖单，买入及撤单 |
| 证据 | 检查承诺遗漏和同成员同轮冲突清单的真签名 |

理想密钥保管器不是门限加密；它只允许在密码组件尚未接入时研究释放条件和处理流程。本原型不提供真实的串谋保密保证，不测量真实门限密码性能。

## 环境与命令

需要 Go 1.23 或更高版本。无第三方 Go 依赖，无需数据库、Docker、钱包或真实资金。

在项目根目录运行：

```sh
./scripts/go.sh test ./...
./scripts/go.sh run ./cmd/pinocchio run -scenario normal -out runs/normal-01
./scripts/go.sh run ./cmd/pinocchio run -scenario omission -out runs/omission-01
./scripts/go.sh run ./cmd/pinocchio verify -file runs/omission-01/evidence.json
./scripts/go.sh run ./cmd/pinocchio audit -file runs/omission-01/report.json
./scripts/go.sh run ./cmd/pinocchio replay -file runs/normal-01/report.json
```

如果 Go 已在 PATH 中，可以把 `./scripts/go.sh` 换成 `go`。脚本也支持本机 `.tools/go/bin/go` 的工具链。已有输出目录不会被覆盖，请换一个输出目录名。

## 按步骤理解代码

### 1. 签名与加密

用户签名订单及其公开上下文，用每单随机密钥加密该签名订单，再签名完整公开头部、加密随机数和密文。头部包含协议域、会话上下文、登记轮次、用户和命令编号。会话上下文仅绑定公开策略及随机会话编号，不再散列含订单明文的整个场景配置。

AES-GCM 将头部作为附加认证数据；头部可见，但不能与原密文任意替换。订单 ID 由密文核心摘要得到，不包含外层签名。密钥先进入模拟保管器；仅在服务锁序并满足释放条件、成功打开后，才在 `openings` 中公布该订单的密钥，供独立核验。尚未服务订单的密钥不写入输出。

代码：`protocol/crypto.go`、`protocol/types.go`。

### 2. 多节点接收与承诺

每个节点在自己的虚拟投递时间收到包。验证外层签名及上下文，在轮次窗口内且本地额度未满时，签名承诺将该 ID 放入本轮最终完整清单。所有承诺都被记录，模拟网络将其交给证书收集器。

默认 n=5、f=1、q=4、t=3。q 是不同成员的准入签名数；t 在本版仅为理想保管器的释放批准数。两者不是同一个证明。配置检查 n≥3f+1、2q>n+f、q≤n−f 和 f<t≤n−f；这些约束不是已经实现共识的证明。

本版假定签名成员的已接受订单可以进入其最终清单；没有撤回承诺的协议例外。重复投递不重复承诺；无效外层签名被拒绝，不使整个案例退出。窗口是提交所属登记轮的接收边界，不是订单到期或按期成交保证。窗口外投递不会自动重新提交。

拒绝回复、正常乱序或没有收齐 q 份承诺，都不单独证明节点违规。

### 3. 最终清单、核查与共同登记

每轮所有成员发布按 ID 排序去重的完整清单。理想协调器选取每成员一份清单，合并并去重，只接纳拥有 q 份有效同上下文承诺的订单。

同时，检查器将某成员的承诺与该成员本轮签署的完整清单比较。签名有效而清单缺单时，输出两份签名作为遗漏证据；同一成员签署两份不同的规范最终清单时，输出冲突证据。别的成员仍可能把订单带入共同登记，因此“某节点违规”和“订单全局丢失”是两个结果。

本版依赖所有成员均发布清单，并由理想协调器共同确认所选集合。缺失清单、协调器分叉、广播可用性与异步活性尚未实现。输出中的 `ideal_registry` 是模拟协调器记录，不是共识证书。

### 4. 持久等待队列

同轮按公开的 `(owner, nonce, ciphertext digest)` 排序后追加至队尾，后续轮不能插到已登记队列前。这个排序只是确定性占位规则，会受到身份选择影响，不代表真实先到先得，也不是孔多塞排序。

本版限制每节点每轮承诺量和每次服务量，尚无全局队列总容量、预付资源票据、拥塞价格或最大等待时间保证。没有取得证书的订单不登记，也不会强迫解密。

### 5. 服务锁序与释放

取队首至多 C 笔订单，绑定精确的有序 ID 列表摘要。理想最终确认组件生成成员服务签名并安装锁序记录；保管器只允许打开这份锁中出现的订单，还要求 t 个不同成员对该服务轮、上下文和名单摘要的有效释放批准。

本版这些签名由单进程协调器驱动，并没有实现分布式投票、视图切换或真实份额广播。已登记但没轮到服务的订单保持密文。服务确认与解密、执行之间暂不模拟真实耗时，因此事件时间不能用于宣称实际加密延迟。

### 6. 解密和业务执行

验证正文授权、用户和编号，再按已锁顺序处理。一笔 YES 卖单初始有 10 份锁定库存，每份 60 分；Alice、Bob、Carol 默认各有 1000 分。

- 买入：检查限价、余额及可成交库存；库存不足可部分成交，余额不足则本次不成交。
- 撤单：只有卖家能撤销剩余库存；已成交份额不能追回。
- 每个用户/命令编号至多处理一次，包括处理后因业务条件失败的命令；不要求编号连续。
- 资金和 YES 份额守恒。没有 AMM、预言机结算、NO 份额撮合或现实赛果认证。

承诺阶段不预留交易金额。余额不足会占用处理资源但无法付款，是明确保留的攻击面。本版没有费用、罚没或业务资金预锁定。

## 内置场景

| 场景名 | 修改了什么 | 预期观察 |
|---|---|---|
| normal | 正常流程，服务容量为 1 | Alice、Bob、Carol 跨轮依次处理 |
| delay | 不同成员收到不同顺序 | 没有违规证据 |
| omission | node-1 承诺后发布空清单 | 产生遗漏证据，其他成员仍可帮助登记 |
| refusal | node-1 拒绝承诺 | 其余 4 个签名仍足够，没有说谎证据 |
| equivocation | node-1 额外签署冲突最终清单 | 产生冲突证据 |
| late | Alice 的包到达时窗口已关闭 | Alice 不登记、不解密；不据此判恶 |
| capacity | 每节点每轮只接 1 笔 | 拒绝后来的申请，不驱逐已登记订单 |
| funds | Alice 初始余额只有 100 分 | 登记后执行失败，原因是余额不足 |
| cancel | 加入卖家撤单 | 按同一队列处理，后续买单可能没有库存 |
| duplicate | 每次消息多投递两份 | 重复包不增加承诺、名次或成交次数 |
| corrupt | 对 node-1 的投递损坏签名 | 拒绝坏包，其他四节点仍可支持登记 |
| drop | 丢弃发往 node-1 的消息 | 没有收包记录，不凭丢包认定节点说谎 |

这些是功能性案例，不是已经测得的攻击防护率或性能实验。

## 输出与核查

- `report.json`：配置、流程事件、密文包、签名、证书、证据和市场结果。
- `events.jsonl`：逐行时间线。
- `metrics.json`：投递、拒绝、登记、处理、成交及证据计数；不表示真实网络吞吐。
- `evidence.json`：只含公开成员密钥、上下文和被指控的签名对；检查器不读取隐含投递时间。

报告配置含模拟订单明文，用于实验重放。输出不是生产系统的隐私日志。签名私钥与尚未服务订单的 AES 密钥不写出；已处理订单的 AES 密钥公开用于核验，模拟器本身掌握完整状态。

`verify` 证明给定证据在给定成员公钥下存在签名矛盾，不证明成员的现实身份，也不证明证据集合完整。公钥必须来自可信配置；攻击者可以另造一套公钥和自签数据，所以不能将整个证据文件当作自动可信的身份根。

`replay` 根据配置与种子重新运行并比较语义事件、执行结果和最终市场状态。每次使用新的真实随机密钥、随机数和签名身份，因此完整文件不会逐字节相同。这个命令不是完整报告的安全审计，不核验其中所有签名字段。

`audit` 不调用模拟器或撮合执行器：核对公钥集合、外层签名、承诺及证书、完整清单、登记并集、服务队首、释放批准、AES-GCM 打开及内层签名，再独立核算结果与账本。它还能检查公开材料中遗漏的已知矛盾证据。它不能证明现实身份、公钥来源、日志未被整体替换或真实投递时间。

可用 `./scripts/demo.sh runs/my-v02-suite` 一次运行全部十二个案例并逐一审计和重放。

## 本版测试覆盖

正常与故障场景、跨轮不插队、锁序前不释放、重复签名不能凑门限、证据篡改与跨上下文复用、余额不足、资金及份额守恒、语义重放。

## 后续替换顺序

1. 固化承诺的容量/费用条件、完整清单规则和缺失清单处理。
2. 将单进程消息投递换为真实进程及网络，保留协议检查函数。
3. 接入共同登记与服务确认的共识实现。
4. 替换 IdealVault，采用经评估的门限密码组件。
5. 增加独立审计者、真实密码测量与可视化。

本版不声称整体协议已证明安全、新颖或优于 Shutter＋Primev。
