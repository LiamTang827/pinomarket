# 第一版设计范围

状态：设计草案，尚未实现。此文件是理解和实现的起点，不是完整协议规范或安全证明。

## 两个目标

1. 重放一笔订单从提交到处理完成的过程。
2. 检查节点的已签声明与后续记录之间是否存在可验证矛盾。

市场仿真和节点问责共用事件记录。仿真器掌握的全局真相不能直接当作现实验证者可获得的证据。

## 基础流程

| 阶段 | 含义 | 不能据此宣称什么 |
|---|---|---|
| 提交 | 用户发送密文订单 | 不代表成员已接受 |
| 准入承诺 | 成员承诺把订单放入本轮完整清单 | 不代表已取得全局位置或保证成交 |
| 共同登记 | 选定完整清单并合并、去重，确认队列 | 不自动证明同轮先到先得 |
| 服务确认 | 最终确定本次处理的队首名单和顺序 | 不能仅凭负责人通知就解密 |
| 解密与执行 | 获得足够份额后按确定顺序处理 | 仍可能因余额、限价或库存失败 |

## 最小场景

- 一个 YES/NO 市场，事先存在库存已锁定的卖单。
- 买入和撤销已有卖单使用同一处理流程。
- 首先比较公开订单和理想化隐藏内容模式，再接入真实密码操作。
- 使用有限队列与服务容量；参数作为配置，不能随意改变安全阈值。
- 五个成员、最多一个故障、四个准入签名和三个解密份额可作后续示例配置；它们不等于已经完成的共识实现。

## 优先定义的证据

| 候选证据 | 成立前提 |
|---|---|
| 同轮冲突的最终清单 | 绑定同一主体、轮次与上下文，并明确禁止相互替换 |
| 承诺后在本地完整清单中遗漏 | 能取得完整清单或可靠的不包含证明；没有适用的协议例外 |
| 超额承诺 | 能核对同轮额度及足够多份不同订单的有效签名 |

同一轮的不同成员可以有不同本地清单。只有比较同一成员在同一上下文中的义务和声明，才能判断是否矛盾。

下一步将研究带本地编号和摘要连接的接受记录。这只是候选扩展：编号描述已确认的接受次序，不证明首次网络接收次序，也不直接决定全局排序。

## 不判为说谎的情形

- 不同成员报告不同接收顺序。
- 用户发出请求，但没有可验证的节点接收记录。
- 消息超时，但无法区分故障、延迟或故意忽略。
- 订单按规定顺序执行，却因余额不足或库存消失而失败。

## 核验方式

每个案例分别保存：输入与配置、仿真调度记录、节点实际签署的证据、执行结果、检查器判断。

先构造正常案例与一个能明确证明矛盾的案例，再加入延迟、乱序、重复消息和重启。检测率、误报率、等待轮数和消息开销的含义需要先定义，之后再报告数值。
