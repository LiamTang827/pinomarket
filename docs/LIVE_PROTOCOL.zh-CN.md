## 1. 参与方和受信边界

用户钱包生成并签署交易。节点负责受理、签发时间证据、参与共识，并持有门限解密份额。本地演示使用五个独立进程，允许的故障数参数为 `f = 1`，共同登记和时间证明所需签名数为 `q = 4`，解密所需份额数为 `t = 3`。两个门槛分别用于确定共同依据和恢复交易内容。密钥生成由本地初始化器协调，它能接触各节点的份额。

受理组件给密文的受理顺序和轮末名单签名。在当前软件实现里，签名密钥和时钟都由宿主管理。将来接入硬件时，需要验证签名密钥来自经证明的代码、该代码从可信来源取得时间，以及宿主不能回滚日志或绕过接收路径。

## 2. 一笔交易怎么处理

1. **提交密文。** 钱包用随机对称密钥加密签名后的交易，再用委员会公钥加密这把密钥。公开头和密文由用户签名绑定。
2. **形成时间证书。** 客户端先把密文交给入口节点取得本轮时间证书。入口与验证节点进行带随机挑战值的签名校准。校准完成后，入口给这笔密文签发时间声明，验证节点按估计的传播延迟检查该声明。证书收齐规定数量的不同节点签名，并绑定网络、轮次、入口、密文标识和被认可的时间。
3. **受理与登记。** 客户端把同一个密文和证书发给多个节点。节点核验材料，按本轮额度受理，在本地顺序日志记录受理并签名。窗口关闭后，节点从受理日志生成带签名的轮末名单。共同状态验证名单、证书和封存记录，从共识选定的名单中去重并登记交易。
4. **按规则排序。** 已登记的轮次保持先后，同一轮按证书时间排序，时间相同按密文标识排序。同一密文出现多份合格证书时，在所选名单中的证书里取最早时间，再用证书哈希打破平局。节点通过同一状态规则重算这些结果。
5. **先锁定，再揭示。** CometBFT 确认队列头部本批要处理的精确名单及顺序，锁定标识绑定其有序密文标识。节点在锁定确认后提交对应的解密份额。每笔交易收齐足够有效份额后，恢复对应的对称密钥，核验用户授权并按锁定顺序处理。执行时仍会检查余额和库存。

这里的 **commit–reveal** 指共识先提交有序密文名单，然后由委员会门限揭示正文。交易用户无需回来提供密钥。用户仍会收到签名受理回执，节点继续推进登记无需用户再次上传整份回执。

## 3. 时间证据能说明什么

延迟校准借鉴了 Aion 的挑战和时间校正思路。验证节点收到入口的签名挑战应答时，用本地时间减去应答里的入口时间，得到该轮的延迟估计 `d`。之后收到入口对一笔密文声明的时间 `s`，验证节点记下自己的接收时间 `r`，在 `abs((r - d) - s) <= δ + ε` 时才能认可声明。其中 `δ` 是配置的时钟偏差容差，`ε` 是延迟波动容差。证书保留入口声明 `s` 和验证节点签名的接收时间、延迟估计。完整挑战过程由各验证节点本地校验。[Aion 原文](https://gramoli.github.io/pubs/ESORICS23-Aion.pdf)

这个时间是在入口校准完成后记录的。用户点击发送、入口最早收到包、其他节点实际受理是不同的时刻。同轮内，客户端可以先取得证书，再选择何时送去受理，这段等待不计入排序时间。路径和排队延迟会变化，时钟也可能超出配置容差。接近窗口边界的交易还受共识进度影响。原论文的公平性证明不能直接迁移到这套证书与排序规则。

节点可以验证已签材料是否绑定同一密文、轮次及证书时间。进入受理组件之前，宿主或网络仍可能延迟或丢弃请求。本机软件密钥泄露时也可能伪造记录。达不到门限、共识停顿或队列拥堵时，处理可能延后。收到回执、进入共同登记、锁定执行位置和实际成交是四个不同的状态。

## 4. 容量和通信

队列容量为 `Q`，开窗时已占用 `U` 个位置，`n` 个节点各有 `floor((Q - U) / n)` 个本轮本地受理额度。即使节点受理的交易完全不同，合并名单也能放进预留容量。重复受理和未用完的额度会让实际新增交易数低于预留量。

每份时间证书携带 `q` 份验证签名。把证书发给至多 `n` 个节点受理时，客户端这一段传输至多携带 `n × q` 份验证签名的副本。入口还要向多个验证节点申请校准及投票。延迟估计按轮缓存，同一轮相同入口与验证节点之间的挑战可以复用。多个请求可以并行，签名数不能直接换算成网络往返数。共同名单、共识和解密份额的通信另计。

可通过节点的 `/metrics` 查看四条时间证据路由的请求次数和 HTTP 正文大小。统计范围是应用层。共识流量和网络封装需要另测。[基础协议复杂度推导](COMPLEXITY.zh-CN.md)

## 5. 运行与核验

从仓库目录运行下面的命令，每次使用新的输出目录。

```sh
bash scripts/network-demo.sh runs/first-demo
./scripts/go.sh test ./...
```

演示启动独立节点并写出回执和 `audit.json`。审计重放共同状态，核对共识签名、门限解密结果和执行状态。运行目录还包含私钥和秘密份额，分享时只挑选需要的公开文件。

手动初始化可指定软件受理和时间证书排序模式。

```sh
mkdir -p bin
./scripts/go.sh build -o bin/pinocchio ./cmd/pinocchio
bin/pinocchio network init -dir runs/manual -ordering aion -ingress software
```

分别启动 `node0.json` 至 `node4.json` 的节点进程，然后运行 `ready`、`open`、`submit`、`wait`、`audit`。客户端命令带 `-dir runs/manual`，节点命令带 `-config runs/manual/node0.json` 等各自配置。可用 `bin/pinocchio network init -h` 查看时间容差、窗口和容量参数。

使用 `submit -out` 时，客户端会先把附证书的密文写到文件，再请求节点受理。重试用 `submit -packet` 读取原文件，并提供新的 `-out` 路径。
