# Pinomarket 本地开销样本报告

日期：2026 年 10 月 25 日。硬件：Apple M2，16 GiB 内存，arm64；软件与源码摘要见 provenance.json。

## 一、测量目的

在现有协议上增加可核查的通信、计算、资源与阶段延迟统计，先观察正常处理六笔订单的成本。本轮没有 AI 决策、攻击场景或新排序机制，不把结果作为安全证明或吞吐上限。

## 二、设置与有效性

- 五节点、八节点各两次，共四组正式样本；每组提交六笔单份买单，全部完成登记和处理，独立审计通过。
- 解密门槛均为 3，服务容量均为 2，接单窗口 20 个区块，最小区块间隔 300ms；队列容量分别为 30/48，使每节点额度同为 6。
- 五节点参数为 f=1、q=4；八节点为 f=2、q=6。节点数变化时，共识门槛和配置验证工作也随之变化。
- 每 500ms 尝试采集状态、网络计数与进程资源；计数器起止采集跨数毫秒，并非同时快照。观察端点流量另列，其计算成本仍包含在节点 CPU 中。
- 初始化、DKG、启动与审计不计入负载区间。负载快照冻结后先审计、停止全部节点，再测 14 项本地 API；每项 3 次预热、30 次正式调用。

## 三、通信与资源结果

以下范围为同配置的两次实际样本；MiB=2²⁰ 字节、KiB=2¹⁰ 字节，未作空闲基线扣除。

| 指标 | 五节点（两次） | 八节点（两次） |
|---|---:|---:|
| 全部节点完成的观测区间（秒） | 21.64–22.63 | 24.70–25.17 |
| 共识发送数据包（MiB） | 3.56–3.78 | 16.70–16.83 |
| 协议 HTTP 正文（MiB） | 2.35–2.44 | 7.47–7.55 |
| 已测协议部分合计（MiB） | 5.92–6.22 | 24.18–24.38 |
| 按处理订单归一化（KiB/笔） | 1009.69–1060.95 | 4126.16–4160.21 |
| 另列：观察 HTTP 正文（MiB） | 6.22–6.74 | 16.90–17.62 |
| 节点累计 CPU 时间合计（秒） | 17.79–19.54 | 44.85–45.81 |
| 节点 RSS 采样最大合计（MiB） | 304.27–311.17 | 535.66–542.19 |
| 各组提交到处理延迟中位数（秒） | 18.68–19.30 | 20.42–20.59 |
| 有限负载处理速率（笔/秒） | 0.265–0.277 | 0.238–0.243 |
| 完成的 gossip 请求数 | 1660–1720 | 5320–5376 |

协议合计只加应用 HTTP 正文和共识发送侧 MConnection 包计数，不含 HTTP 头、完整加密链路/TCP/IP 开销、本地 Comet RPC或观察请求。因此不能称为完整物理线上流量。每笔结果是有限区间归一化，不能当作通信复杂度定理。

## 四、计算操作结果

单位为毫秒/调用。每栏为两次运行全部 60 个正式调用的平均值；详细逐次样本、p50/p95和被调用的完整步骤在 computation.json。

| 操作 | 五节点配置 | 八节点配置 |
|---|---:|---:|
| 承诺签名 | 0.0194 | 0.0185 |
| 承诺验证 | 0.0405 | 0.0413 |
| 完整订单创建 | 1.7868 | 1.9518 |
| 完整密文包验证 | 0.5724 | 0.7751 |
| 随机密钥门限加密 | 1.7021 | 1.9012 |
| 生成并内部验证一个解密份额 | 2.3336 | 2.8339 |
| 验证一个解密份额 | 1.6514 | 1.9253 |
| 验证三份额并重构、解密密钥 | 6.5040 | 7.2571 |
| 完整订单打开 | 6.5199 | 7.3146 |
| 四订单名单验证 | 2.5396 | 3.3210 |

完整订单打开包含门限解密，生成份额也包含内部验证。各行存在包含关系，不能相加估计总成本。门限配置验证、曲线点检查与反复签验都保留在当前 API 中；该表测量当前实现，不代表密码库的最小可能开销。

## 五、目前观察到什么

1. 两个规模的六笔订单均可完成，并能产出可独立检查的资源数据。八节点在本机样本中的通信和累计 CPU 用量高于五节点；仅两个规模不能反推出渐近复杂度。
2. 收据传播值得进一步检查。五节点完成 1660–1720 次 gossip 请求，八节点完成 5320–5376 次；程序在订单已经处理后仍可能轮转旧收据。流量取决于运行时长和重试次数。这里没有改变传播规则。
3. 单次门限份额验证、密钥重构和订单打开明显比单次普通承诺签验耗时，但尚未做 CPU profiling，不能据此断言它们占总 CPU 的百分之多少。
4. 观察接口本身会产生较大流量。它单独列出，但仍给节点带来序列化与采样负担，后续严肃性能比较应加入更轻的观察方式或测量开销对照。

## 六、失败与补跑记录

最初四次启动在节点就绪后、开窗之前，Python 监控请求出现 RemoteDisconnected，没有提交订单。随后将本机请求改为显式禁用代理、限制 loopback URL并补充测试；一个五节点试运行通过，之后四组正式样本均通过。初始错误与默认代理路径相符，但没有保留足以单独证明代理为根因的抓包，故仅报告修正及观察结果。

总计保留九次网络启动：四次开窗前采集失败、一次有效试运行、四次正式样本。试运行不并入正式比较，初始失败不计作协议攻击或未成交。原始记录全部留在本地忽略目录。

## 七、还不能回答什么

- 没有未加密基线或去掉承诺的对照，不能量化“门限加密额外增加多少”或“承诺额外增加多少”。
- 没有长时间持续负载、并发扫描或 WAN 部署，不能把约 0.24–0.28 笔/秒当作吞吐上限。
- 尚未测量 DKG、启动、轮换成员、在线 AI 决策或经济激励的成本。
- 每配置只有两次正式运行。所有阶段时间是客户端首次观察值，不证明真实首次接收时间或公平排序。

下一步可先补“空闲网络对照”和更轻量的观察器，随后针对重复传播或重复验证做一次单独优化，并在同负载下比较前后差异。
